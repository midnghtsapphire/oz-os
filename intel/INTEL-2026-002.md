# pull_request_target + checkout PR head = RCE risk

## What we learned
The `pull_request_target` event runs with the **base branch's** workflow file
but has access to repo secrets. If a workflow using this event then checks out
the PR head (`actions/checkout` with `ref: ${{ github.event.pull_request.head.sha }}`),
an attacker can submit a malicious PR that modifies the workflow script and
executes arbitrary code with write access to the repository and all its secrets.

This is a known attack vector documented by GitHub Security Lab as "pwn requests."

## Why it matters
Several revvel-standards workflows use `pull_request_target`. Any that also check
out the PR head code are vulnerable. An attacker could exfiltrate all repository
secrets (including API keys) or push malicious code directly to `main`.

## How to apply it
1. Audit all workflows using `pull_request_target` — ensure they do NOT checkout PR head
2. If PR head checkout is needed, use a two-job pattern: first job runs trusted code
   to validate, second job only runs after approval
3. Prefer `pull_request` event over `pull_request_target` unless secrets are required

## When it stops being true
This is a fundamental GitHub Actions design constraint. It stops being true only if
GitHub changes how `pull_request_target` works, which is unlikely given backward
compatibility concerns.
