# gh issue list --limit 1000 silently truncates

## What we learned
The `gh issue list --limit 1000` command and the GitHub REST API endpoint for
listing issues have a maximum page size. When a repository has more than 1000
open issues, the command returns only the first 1000 without any warning or
error. Scripts that depend on "all issues" silently miss the rest.

The GitHub REST API paginates at 100 per page by default, and the GraphQL API
has its own node limits. Neither surfaces a "you have more results" warning in
a way that naive scripts catch.

## Why it matters
Any automation that processes "all issues" (e.g., WR trackers, stale-issue
detectors, dashboard generators) will produce incomplete results on repos with
high issue counts. `revvel-standards` is approaching this threshold.

## How to apply it
1. Always use pagination: loop until the response returns fewer items than the
   page size, or use the `Link` header's `rel="next"`
2. For `gh` CLI: use `--paginate` flag or `--json` with `jq` to detect truncation
3. For critical counts, verify with `gh api repos/{owner}/{repo}` and check
   the `open_issues_count` field against what the list returned
4. Add a sanity check to any script that expects a complete issue list

## When it stops being true
If GitHub CLI adds a `--warn-on-truncation` flag or changes the default behavior
to auto-paginate. Check GitHub CLI changelog periodically.
